# 高级案例：控件检索工作流

控件检索器适合用来把“我想点这个按钮”变成可维护的规则锚点。它不是最终自动化规则，而是规则开发阶段的观察工具。

## 工作流

```text
打开目标页面
  -> 启动控件检索器
  -> 点选目标区域
  -> 读取节点属性
  -> 选择稳定锚点
  -> 写入动作链
  -> 回到目标页面验证
```

真实控件检索器会用悬浮按钮选择位置，再根据坐标寻找最合适的无障碍节点，并展示属性面板。

## 读属性时看什么

| 属性 | 怎么用 |
| --- | --- |
| `viewId` | 首选锚点，迁移后通常比文本稳定 |
| `text` / `description` | 适合按钮和菜单，但要注意多语言 |
| `className` | 区分输入框、按钮、列表、容器 |
| `bounds` | 辅助坐标点击或截图区域 |
| `clickable` | 决定点当前节点还是点父节点 |
| `editable` | 决定能否输入文本 |
| `scrollable` | 决定是否要先滚动 |
| 父子路径 | 文本重复时定位具体位置 |

不要只复制坐标。坐标是最后兜底，节点属性才是长期维护的依据。

## 从检索结果到规则

如果检索结果能给出稳定 `viewId`，优先使用节点查找或节点点击动作。若只有文本稳定，则把文本匹配和页面校验放在一起：

```text
等待目标页面出现
  -> 查找包含目标文本的节点
  -> 校验 Activity 或附近文本
  -> 点击节点或父节点
  -> 输出执行结果
```

如果节点不可见，但屏幕区域稳定，再使用坐标或 OCR：

```text
节点查找失败
  -> 截取固定区域
  -> OCR / 找图
  -> 计算坐标
  -> 点击
```

## 开发期与发布期分离

控件检索器里可以有大量悬浮窗、动画、属性面板和导航按钮；正式规则不应该保留这些 UI。正式规则只需要：

- 目标页面判断。
- 稳定锚点。
- 等待和超时。
- 执行动作。
- 失败输出。

这能显著降低误触、残留悬浮层和跨设备适配风险。

## 常见误区

| 误区 | 后果 |
| --- | --- |
| 只用文本定位 | 多语言、版本更新后失效 |
| 只用坐标点击 | 分辨率、横竖屏、显示缩放后失效 |
| 不校验页面 | 同名控件在错误页面被点击 |
| 不处理等待 | 页面动画未结束导致节点为空 |
| 把检索器 UI 当正式规则 | 维护成本高，失败后难排查 |

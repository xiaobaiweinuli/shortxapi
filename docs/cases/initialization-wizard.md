# 初始化向导

复杂规则第一次启用时通常不能直接运行。它们需要创建变量、让用户选择目标应用、创建应用集、检查依赖，甚至在初始化失败时自动禁用自己。

## 推荐结构

```text
hook.actionsOnEnabled
  -> 检查全局变量是否存在
  -> 不存在则创建
  -> 弹出对话框收集配置
  -> 创建应用集或默认配置
  -> 关键配置缺失时禁用规则

hook.actionsOnDeleted
  -> 清理规则创建的状态
```

初始化动作属于规则生命周期，不属于主触发链。导入审查时必须单独阅读。

## 创建去重变量

验证码类规则常用去重变量：

```json
{
  "@type": "type.googleapis.com/CreateGlobalVar",
  "globalVar": {
    "name": "sms_dedup_hash",
    "type": {
      "@type": "type.googleapis.com/StringVar"
    }
  }
}
```

删除规则时清理：

```json
{
  "@type": "type.googleapis.com/DeleteGlobalVar",
  "varName": "sms_dedup_hash"
}
```

这类变量是规则内部状态，通常不需要迁移到新设备。

## 用户选择配置

代理类规则需要选择代理工具。真实流程大致是：

1. 扫描具备 VPN AppOps 能力的应用。
2. 输出可显示列表。
3. `ShowListDialog` 让用户选择。
4. 把选择结果写入 `代理工具` 全局变量。

文档化时要把扫描和选择分开说明。扫描结果可能因设备、用户、权限和 ROM 变化而不同，不应写成固定列表。

## 创建应用集

应用集用于让用户维护一组目标包：

```json
{
  "@type": "type.googleapis.com/CreatePkgSet",
  "label": "Proxy"
}
```

创建后，规则说明应告诉用户：

- 应用集叫什么。
- 需要把哪些 App 加进去。
- 应用集为空时规则会怎么做。
- 删除规则时是否删除应用集。

如果应用集是用户长期维护的配置，删除规则时不一定自动删除，但必须在说明里写清楚。

## 初始化失败时自禁用

规则可以在关键配置缺失时弹出说明，并用 `SetRuleEnabled` 禁用自身。这比让规则半配置状态下继续触发更可靠。

适用场景：

- 用户取消了目标应用选择。
- 必要全局变量创建失败。
- 外部插件不存在。
- 应用集为空。
- 规则需要的系统能力不可用。

自禁用不是错误，而是一种保护。

## 避免重复初始化

启用 hook 可能被多次执行，所以初始化动作应先判断状态是否存在：

```text
EvaluateGlobalVar IsNotExists
  -> CreateGlobalVar
```

不要每次启用都覆盖用户配置。只有去重缓存、临时状态或明确的重置流程才适合重写。

## 说明文案应该写什么

初始化型规则的发布说明至少包括：

- 第一次启用会创建哪些全局变量。
- 会创建哪些应用集。
- 用户需要手动填什么。
- 删除规则时会自动清理哪些内容。
- 哪些内容不会自动删除。
- 初始化失败时规则是否会自动禁用。

## 检查清单

- 是否先判断变量存在，再创建？
- 是否避免覆盖用户已有配置？
- 关键配置是否有取消分支？
- 用户取消后是否禁用规则或停止主流程？
- 删除 hook 是否清理内部状态？
- 应用集和全局变量的归属是否写清楚？
- 初始化动作是否只做配置，不执行高风险主动作？

初始化向导的核心价值是让复杂规则“可首次运行、可迁移、可删除”。没有初始化边界的复杂规则，后期维护成本会非常高。

# 触发策略

复杂自动规则通常不只有一个触发器。复杂自动规则经常把定时、应用前台、DeepLink、输入法显示、按键事件放在同一条规则里，再用 tag 和条件决定当前走哪条分支。

## 多触发器结构

常见结构：

```text
facts[]
  -> 每个 fact 可带 tag
conditions[]
  -> 全局快速过滤
actions[]
  -> SwitchCase / IfThenElse
  -> RequireFactTag 区分入口
```

例如清理规则同时有：

- `FixedInPeriod`，tag 为 `定时`。
- `AppBecomeFg`，tag 为 `前台`。
- 可禁用的 `ScreenOn`，tag 为 `亮屏`。

主动作再用 `RequireFactTag` 判断这次到底是哪种入口。

## 为什么要用 tag

tag 能避免不同触发器混在一起：

```json
{
  "@type": "type.googleapis.com/RequireFactTag",
  "tag": "定时"
}
```

推荐用短业务名：

| tag | 用途 |
| --- | --- |
| `定时` | 定期维护、备份、清理 |
| `前台` | 进入某类应用后执行 |
| `关闭` | 目标应用退出或停止运行 |
| `DeepLink` | 外部调用入口 |
| `按键停止` | 停止长任务 |

不要只靠触发器顺序判断入口。导出迁移、禁用某个 fact 或新增触发器后，顺序并不可靠。

## 全局条件与分支条件

全局 `conditions` 应该只做快速过滤，例如：

- 屏幕是否亮。
- 总开关是否开启。
- 当前设备状态是否允许执行。

分支内部再判断入口和业务条件：

```text
conditions: ScreenIsOn

SwitchCase:
  Case 定时:
    RequireFactTag("定时")
  Case 前台:
    RequireFactTag("前台")
```

不要把所有条件都塞到顶层。否则某个入口需要的特殊条件会影响其他入口。

## `IfCondOp`

`IfThenElse` 可以使用 `IfCondOp` 控制多个条件的关系。条件组合里可以使用 `ANY`，表示任意一个入口匹配即可执行。

设计规则：

| 关系 | 用途 |
| --- | --- |
| `ALL` | 必须同时满足，比如前台应用在集合内且网络可用 |
| `ANY` | 多入口共用动作，比如定时或进入文件 App 都可清理 |

如果没有明确设置，阅读导出时要看默认行为，不要猜。

## 高频触发器

高频触发器包括：

- 应用前台变化。
- 通知到达。
- 输入法显示变化。
- 屏幕亮灭。
- 剪贴板变化。

这些触发器应搭配：

- 全局开关。
- 去重状态。
- 冷却时间。
- 应用集过滤。
- `isBreak` 或互斥分支。

否则规则会重复执行，甚至不断弹窗或反复写状态。

## DeepLink 作为人工入口

`DeepLinkCall` 可以把规则变成可外部调用入口。输入法助手类规则会把 `IMEVisibilityChange` 和 `DeepLinkCall` 放在同一规则里：

```text
输入法显示 -> 显示主 Overlay
DeepLinkCall -> 重新显示上一级 Overlay
```

这种设计可以让按钮点击后调用 `shortx://trigger?tag=...` 回到规则入口。要注意：

- DeepLink tag 应稳定。
- 参数名要写清。
- 入口之间要避免递归触发。
- Overlay 关闭动作要先执行，再重新触发入口。

## 禁用备用触发器

复杂规则常保留 `isDisabled: true` 的备用触发器，例如亮屏触发。它们可以作为调试或扩展入口，但默认不运行。

审查时：

- 不把禁用 fact 当作当前入口。
- 启用前确认它是否会高频触发。
- 启用后检查分支条件是否覆盖它。

## 触发策略清单

- 每个入口是否有 tag？
- 顶层条件是否只做通用过滤？
- 分支条件是否用 `RequireFactTag` 区分入口？
- 高频入口是否有去重、冷却或应用集过滤？
- DeepLink 是否会造成递归？
- 禁用触发器启用后是否会落入正确分支？
- 多触发器共享动作时，`ANY` 和 `ALL` 是否明确？

触发策略的目标是让规则“为什么运行”可解释。只有动作正确还不够，入口不清楚的规则最难维护。

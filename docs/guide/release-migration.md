# 发布与迁移

发布 ShortX 一键指令或自动指令，不只是导出一段配置。高级规则往往依赖全局变量、代码库、插件、系统设置、包名、用户 ID 和 ROM 行为。

## 发布前检查

| 项目 | 检查内容 |
| --- | --- |
| 触发器 | 目标应用、事件类型、变量是否明确 |
| 条件 | 是否依赖 ROM 文本、语言、时间、网络状态 |
| 动作输出 | `jsRet`、`mvelRet`、`selectedListItem` 是否被正确消费 |
| 自定义上下文 | `customContextDataKey` 是否命名清晰且无冲突 |
| 全局变量 | 是否需要初始化、清理、导入默认值 |
| 代码库 | 是否依赖某个代码库片段 |
| 插件 | 是否依赖外部 ShortX 插件动作或条件 |
| Android 服务 | 是否依赖特定 Android 版本或 ROM |
| 高风险动作 | 是否有确认、备份和恢复路径 |

## 迁移顺序

推荐迁移顺序：

1. 先导入代码库片段。
2. 再导入全局变量默认配置。
3. 再确认插件和系统能力。
4. 最后导入一键指令或自动指令。
5. 禁用状态下先做手动测试，再启用自动触发。

不要一上来启用自动规则，尤其是包含 Shell、系统设置、配置删除、通知清理、输入注入的规则。

## 依赖说明

发布说明应写清楚：

- ShortX 版本或导出来源。
- 需要的插件。
- 需要的代码库片段。
- 需要的全局变量名。
- 会读取或修改哪些系统状态。
- 失败时如何恢复。

不要只写“导入即可用”。这会隐藏高风险前提。

## 变量命名

迁移规则时，最容易发生冲突的是全局变量和 `customContextDataKey`。

建议：

- 全局变量使用前缀，例如 `sms_dedup_hash`、`settings_snapshot_json`。
- 中间结果使用业务名，例如 `ExtractedCode`、`PackageName`。
- 不使用 `title`、`contentText`、`pkgName` 等上下文名做自定义输出。

## 版本差异

迁移到另一台设备时，要重新验证：

- 通知标题和正文格式。
- 包名、组件名、Activity 名。
- Settings key 是否存在。
- Android 服务签名是否变化。
- OCR 坐标是否受分辨率影响。
- 插件动作是否仍然安装。

跨设备迁移的规则，应尽量把设备相关参数放到全局变量或配置段里。

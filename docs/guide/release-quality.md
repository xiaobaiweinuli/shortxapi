# 发布质量检查

高级 ShortX 规则发布前不能只看“能不能跑一次”。高级规则经常同时依赖动作链、全局变量、代码库、应用集、插件、用户 ID、系统设置和外部库。发布质量检查的目标是让别人导入后能理解、能恢复、能排查。

## 入口检查

| 项目 | 要确认什么 |
| --- | --- |
| 触发器 | 触发条件、tag、是否可能重复触发 |
| 外部调用 | DeepLink 参数、默认值、缺参行为 |
| 生命周期 | 首次启用、删除、停止、冲突处理 |
| 手动入口 | 对话框默认值、取消后的行为 |

多触发器规则必须说明每个 tag 的用途。不要让用户只能靠导出顺序猜入口。

## 数据流检查

- 上游输出是否用 `customContextDataKey` 改成稳定名字。
- 下游是否依赖 `jsRet`、`mvelRet`、`selectedListItem` 等默认名。
- JSON 是否有固定字段。
- 对话框 `__value` 是否能被后续脚本解析。
- 空结果、取消、超时是否有分支。

发布说明里应写清“输入是什么、输出是什么、失败是什么”，而不只是贴脚本。

## 依赖检查

| 依赖 | 检查方式 |
| --- | --- |
| 全局变量 | 名称、类型、默认值、是否含 secret |
| 代码库 | 条目名称、ID、语言、输出契约 |
| 应用集 | 标签、包名、用户 ID |
| 插件 | 插件包名、能力名称、版本要求 |
| 外部库 | dex/jar 路径、版本、用途 |
| Android 版本 | 最低 API、ROM 差异 |
| ShortX 版本 | 是否依赖当前 `IShortX` 方法签名 |

依赖内部服务时，说明当前版本、最小验证方式和失败兜底，不要把内部方法写成稳定公共 API。

## 风险检查

高风险动作至少要有一个保护措施：

| 风险 | 保护措施 |
| --- | --- |
| 删除 ShortX 配置 | 备份、二次确认、展示 ID |
| 修改系统设置 | 记录旧值、提供恢复动作 |
| 用户限制/组策略 | 明确目标用户和解除方式 |
| Shell 命令 | 展示命令、限制参数来源 |
| 跨用户启动 | 保存包名和用户 ID |
| 长任务 | 超时、停止入口、日志 |

如果规则会影响设备可用性，发布说明应把恢复方式放在前面。

## 示例审查

发布前至少跑三类测试：

1. 正常路径：预期输入、预期页面、预期系统状态。
2. 取消路径：对话框取消、选择为空、外部调用缺参数。
3. 异常路径：目标 App 不存在、插件缺失、网络不可用、用户 ID 不匹配。

每次测试记录触发来源、关键上下文值、最终输出和失败日志。

```text
名称：
用途：

全局变量：
代码库：

插件：
最低 Android / ShortX：
会修改的状态：

```

这份说明比导出文件本身更重要。导出告诉用户“是什么”，发布说明告诉用户“如何安全使用”。
